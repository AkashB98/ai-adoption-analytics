# ai-adoption-analytics

**An AI-rollout adoption scorecard: cohort adoption, AI-specific metrics (time to first successful AI task, prompts per active seat, output acceptance rate, AI feature breadth), rule-based customer-health tiers emitted as a stable data contract, and median/MAD usage-anomaly flags over seeded synthetic enterprise accounts — the analytics a customer-success or go-to-market team runs every week after an AI product lands inside a customer.**

Motivation: real job descriptions ask for exactly this workflow — roles like these name AI adoption / utilization analytics as core work:

- **Harvey — Enterprise Customer Success Manager**: adoption rates, utilization, and customer-health reporting for enterprise accounts.
- **Ramp — Customer Activation Manager**: an adoption plan plus the metrics that prove a product rollout is landing.
- **Tutor Intelligence — Applied AI, Go-To-Market**: measuring whether deployed AI is actually being used, not just sold.

This repo is that workflow as a runnable artifact: it proves the author can define adoption precisely, build the **cohort** — a group of accounts that started in the same rollout month, compared like-for-like — measure **utilization** — how much of what was bought is actually used — with metrics that are specific to AI rather than generic SaaS (a login count cannot tell you whether anyone kept an AI output), flag accounts whose health is slipping, publish those health tiers as a versioned contract another system can build on, and gate the whole readout behind a CI check, all reproducibly and with no real customer data.

> **Synthetic data only.** Every account is fictional (invented names like Aster Labs and Beacon Group, generated by a seeded generator). No real company, customer, or user data is used anywhere in this project. Company names above are cited only as the job descriptions that motivated the build.

Stdlib-only Python — deliberately. An adoption scorecard is an audit artifact: anyone should be able to read every line of the math, re-run it offline, and get byte-identical outputs. Zero network, zero API keys, zero external dependencies.

## Quickstart

```bash
# 1. Generate the synthetic dataset (120 accounts, 26 weeks, seed 42)
python3 cli.py generate --out dataset.json

# 2. Cohort adoption: activation + week-4 / week-12 retention
python3 cli.py cohorts

# 3. Utilization: seats, sessions per user, feature breadth, scores
python3 cli.py utilization

# 4. AI-specific metrics: time to first successful AI task,
#    prompts per active seat, output acceptance rate
python3 cli.py ai-metrics

# 5. Health tiers + sudden-drop anomaly flags
python3 cli.py health

# 6. Health tiers as the stable v1.0 contract (JSON or CSV) -
#    the output a downstream renewals forecaster would consume
python3 cli.py health-contract
python3 cli.py health-contract --format csv

# 7. Full scorecard report (JSON, or readable text with --format text)
python3 cli.py report
python3 cli.py report --format text

# 8. CI gate: exit 0 = at-risk share within threshold,
#    1 = breach, 2 = data / IO error
python3 cli.py check; echo $?    # 0 on the seeded dataset

# 9. One-command end-to-end demo (generate -> report -> check -> serve)
python3 demo.py

# 10. Tiny localhost API: POST /report, GET /report, GET /health
python3 cli.py serve --port 8765
curl -s -X POST localhost:8765/report -d '{}'   # seeded dataset report
```

## The seeded rollout at a glance (seed 42, 120 accounts, 2,400 account-weeks)

120 fictional accounts roll out in four monthly cohorts (30 each) over 26 weeks starting 2026-01-05. **Activation** — first real use, defined precisely below — lands at **101/120 accounts (84.2%)**.

| Cohort | Accounts | Activation rate | Week-4 retention | Week-12 retention |
|---|---|---|---|---|
| 2026-01 | 30 | 90.0% | 100% | 85.2% |
| 2026-02 | 30 | 83.3% | 100% | 88.0% |
| 2026-03 | 30 | 86.7% | 100% | 96.2% |
| 2026-04 | 30 | 76.7% | 100% | 73.9% |

**Utilization** (last observed week per account): mean utilization score **0.414**, mean **seat utilization** — active users ÷ licensed seats — **29.5%**, and **7,807 of 28,049** licensed seats active overall (27.8%). Mean **feature breadth** — distinct features used ÷ the 8 available — is **0.556**.

**AI-specific metrics** (the numbers generic SaaS analytics cannot give you): **time to first successful AI task** — days from rollout to the first week with a kept AI output — has median **0 days** and mean **2.3 days** (73.3% of accounts kept an output in their very first week; all 120 got there). **Prompts per active seat** — prompts / AI actions submitted per active user, last week — averages **16.4**, from **3,182,142** prompts overall. **Output acceptance rate** — AI outputs accepted (kept) ÷ outputs generated — is **77.0%** (2,450,533 of 3,182,142 outputs kept).

**Customer health** — a rule-based tier for every account (rules below):

| Tier | Accounts | Share |
|---|---|---|
| Thriving | 37 | 30.8% |
| Steady | 34 | 28.3% |
| At-risk | 25 | 20.8% |
| Dormant | 24 | 20.0% |

The **at-risk share** — accounts in at-risk + dormant, the number the `check` gate judges — is **40.8%** against a stated threshold of 50%, so the seeded rollout passes its own gate (exit 0). The anomaly detector raises **125 sudden-drop flags across 72 accounts** — a high count, reported rather than tuned away: this synthetic fleet is decline-heavy by construction (35% of accounts follow at-risk or dormant trajectories), and a sensitive early-warning detector flags real declining weeks, not just the 5 planted craters. All **5 planted anomalies are caught** at their planted week (robust z from −3.68 to −6.75, pinned by eval E11).

## How it works

**Activation, defined precisely.** An account is *activated* iff, in at least one of its first two observed weeks (weeks 0–1 after rollout — the 14-day window), it records **active users ≥ 3 AND sessions ≥ 5**. Both floors matter: one curious login is not adoption, and three users with one session each is not real use either. Every number in this repo uses this one definition (`cohorts.py`).

**Retention, with honest denominators.** Week-N **retention** — the share still using the product at week N — is computed only over *activated* accounts that actually have an observed week-N record. An account whose rollout is too recent to have a week 12 is excluded from the week-12 denominator, never silently counted as churned. (On the seeded data week-4 retention is 100% in every cohort: accounts that clear the activation bar are still ramping at week 4; the separation shows up by week 12, which is exactly why both horizons are reported.)

**Utilization score.** Per account, from its last observed week (current state, not a lifetime average that would hide a recent collapse): `0.5 × seat utilization + 0.3 × min(sessions per active user ÷ 10, 1) + 0.2 × feature breadth`. The weights live in one place in `utilization.py` so they can be argued with and changed in one place.

**AI-specific metrics** (`ai_metrics.py`). Four signals that only make sense for an AI product, each defined once and pinned by eval E15: (1) **time to first successful AI task** — days from rollout to the first week with at least one *accepted* AI output, at weekly resolution (week index × 7, the start of that week); the AI version of time-to-value, reported as median + mean overall and per cohort. (2) **Prompts per active seat** — prompts / AI actions per active user in the last observed week: how hard the people who show up actually lean on the AI. (3) **Output acceptance rate** — outputs accepted (kept in the user's work) ÷ outputs generated, cumulative: the quality signal raw usage hides, since heavy prompting with a low kept share means the AI is being fought, not adopted. (4) **AI feature breadth** — distinct AI features used ÷ the 8 available (chat, summarisation, search, workflow automation, report writing, code help, meeting notes, data analysis): whether use is spreading across the AI surface or stuck in one corner.

**Health tiers — rules in code as data.** `health.HEALTH_RULES` is a data table, evaluated in order, first match wins: **dormant** (no active users in either of the last two observed weeks) → **thriving** (score ≥ 0.60 *and* breadth ≥ 0.50 *and* seat utilization ≥ 0.35) → **at-risk** (score < 0.30 *or* seat utilization < 0.08) → **steady** (everything else). A customer-success manager can read, dispute, and retune the rules without touching control flow — and the evals pin both the rule order and the seeded tier counts, so a quiet rule edit fails loudly.

**Anomaly flags — rolling median / MAD, the only method.** For each week with at least 4 prior weeks, the **baseline** — the account's own recent normal — is the *median* sessions of the previous 4 weeks, and the spread is the **MAD** — median absolute deviation, the median of |value − median| over the same window, a spread measure that a spike cannot inflate the way it inflates a standard deviation. The **robust z-score** — a z-score built from median and MAD instead of mean and standard deviation — is `0.6745 × (current − median) ÷ MAD` (0.6745 puts MAD on a standard-deviation-like scale), and a week flags `sudden_drop` iff robust z ≤ −3.5. One special case: when MAD = 0 (a perfectly flat baseline), any week below the median flags with z reported as the sentinel −999.9 — the true value is unbounded and infinity is not JSON-safe. The generator plants this shape directly: every fifth at-risk account craters to about a sixth of its sessions for one week at week 15 — and all five plants are caught at that week, pinned by eval E11. There is deliberately no second detector and no percent threshold anywhere in the repo; one method, one threshold, argued in one place.

**Health tiers as a stable contract.** `cli.py health-contract` (and the `health_contract` block of the full report) emits the tiers as a versioned **data contract** — a documented, stable output schema another program can rely on — built for a future renewals-forecasting repo to consume without scraping a report. Schema version **1.0**:

| Field | Type | Meaning |
|---|---|---|
| `account_id` | string | stable account identifier (`acct_001`…) |
| `account_name` | string | fictional account name |
| `cohort` | string | rollout month, `YYYY-MM` |
| `segment` | string | `smb` / `midmarket` / `enterprise` |
| `health_tier` | string | one of `thriving` / `steady` / `at-risk` / `dormant` (closed set) |
| `utilization_score` | float | 0..1, last observed week (see `utilization.py`) |
| `seat_utilization` | float | 0..1, last observed week |
| `feature_breadth` | float | 0..1, last observed week |
| `active_users` | int | last observed week |
| `licensed_seats` | int | seats licensed |
| `week_start` | string | ISO date of the last observed week |

Contract rules: records carry *exactly* these fields, in this order, sorted by `account_id`; the JSON form wraps them in `{"schema_version": "1.0", "fields": [...], "tiers": [...], "records": [...]}` and the CSV form (`--format csv`) has the same fields as its header and agrees with the JSON record-for-record (pinned by eval E16). Within major version 1.x, fields are never removed, renamed, or retyped — new fields are only appended, and a breaking change means a new major version.

**The `check` gate.** Exit 0 when the at-risk share is within the stated 50% threshold, exit 1 when it breaches, exit 2 for data-quality or IO errors (validation reports issues, never raises on bad data, so the two failure kinds stay distinct — the same gate discipline as a **CI** — continuous integration, the automated check that runs before code or a report ships — pipeline).

## Architecture

| Module | Job |
|---|---|
| `generator.py` | Deterministic synthetic dataset: 120 fictional accounts, 4 monthly cohorts, 26 weeks; hidden generation archetypes shape trajectories (health tiers are *derived*, never copied from them); AI-usage fields (prompts, outputs generated / accepted) drawn from a separate PRNG stream keyed by (seed, account, week) so they never disturb the session trajectory; 5 planted week-15 session craters; JSON / JSONL serialisers and loaders |
| `cohorts.py` | The activation definition (14-day window, ≥3 users, ≥5 sessions), activation rate, week-4 / week-12 retention with honest denominators |
| `utilization.py` | Seat utilization, sessions per active user, feature breadth, and the weighted utilization score (weights stated once) — per account (last week, incl. prompts per active seat and acceptance rate) and overall |
| `ai_metrics.py` | The AI-specific metrics: time to first successful AI task, prompts per active seat, output acceptance rate, AI feature breadth — per account, overall, and per cohort |
| `health.py` | `HEALTH_RULES` as data → thriving / steady / at-risk / dormant tiers; at-risk share vs the 50% gate threshold; the stable v1.0 health contract (JSON + CSV emitters); rolling median / MAD anomaly detector (the only method) |
| `report.py` | Full scorecard assembly (a pure function of the records, incl. the `ai_metrics` and `health_contract` blocks) + the readable-text rendering — CLI, serve, and evals all read the same numbers |
| `validation.py` | Data-quality gate: required fields, enums, ranges, consistency (no sessions / prompts / outputs without users, accepted ≤ generated), duplicate account-weeks, the int/bool trap — reports issues, never raises |
| `cli.py` | `generate` / `cohorts` / `utilization` / `ai-metrics` / `health` / `health-contract` (JSON + CSV) / `report` (JSON + text) / `check` (CI exit 0/1/2) / `demo` / `serve` (stdlib `http.server` on 127.0.0.1: `POST /report` with `{"records": [...]}` or an empty body for the seeded dataset, `GET /report`, `GET /health`) |
| `demo.py` | End-to-end narrative with asserts: determinism, headline report, check exit codes, live localhost serve round-trip |
| `fixtures/` | `example_records.json` — a tiny 2-account example (one steady, one dormant) that validates clean and is pinned by eval E14 |

## Development loop — what the checks actually caught

1. **A test asserted the display order instead of the evaluation order — and the fix documented a real design decision.** The first full suite run failed one test: it expected `HEALTH_RULES` in display order (thriving, steady, at-risk, dormant), but the rules deliberately evaluate *dormant first* — trailing inactivity must win before any threshold rule can call a dead account "thriving" on stale last-week numbers. The code was right and the test was wrong; the test now pins the evaluation order explicitly, with the reason in a comment, so a future reorder fails loudly instead of silently misclassifying accounts.
2. **Validated design decision: retention denominators exclude the not-yet-eligible.** The obvious implementation (retained ÷ activated) would have punished the April cohort for not having a week 12 yet at short horizons and understated every young cohort. The eligible-only denominator is pinned by a hand case in the tests and eval E8.
3. **The anomaly detector was rebuilt around a single method — and the first plant design failed it.** An earlier draft judged drops by percent-vs-mean; a design cross-check replaced it with one method only, rolling median / MAD, and the rebuild exposed a real calibration problem: at the original plant severity (sessions cut to a third for one week), one of the five planted craters sat at robust z −3.27 — *inside* the −3.5 noise band, uncatchable in principle, because a 4-point MAD is a coarse spread estimate. The plants were made unambiguous (cut to about a sixth) rather than loosening the threshold to fit them: all five now flag at their planted week (z −3.68…−6.75, eval E11), and the threshold stayed where the method put it.
4. **Validated design decision: the MAD window is 4 weeks, not longer.** Longer windows (6–8 weeks) were tried and rejected on the seeded data: they span the rollout ramp, when sessions grow week over week by design, so the median sits far below the recent level and the MAD inflates — the same planted crater that flags at z −5.8 on a 4-week window reads only −2.6 on a 6-week window. A short window is what "the account's own recent normal" means during a rollout.
5. **The seeded week-4 retention of 100% is reported, not tuned away.** It follows from the activation bar (accounts that clear ≥3 users and ≥5 sessions in week 0–1 are, by construction, still ramping at week 4). Rather than weakening the activation definition to manufacture a prettier number, the README says why the number is what it is and leans on week-12 retention — where the cohorts genuinely separate (73.9%–96.2%) — as the discriminating horizon.
6. **The AI-specific metrics and the health contract exist because a cross-check called the first draft "generic SaaS with AI in the title" — fairly.** Logins-and-seats analytics said nothing about whether the AI itself was working, and the health tiers were trapped inside a report no other system could consume. The fix was structural, not cosmetic: prompts / outputs / accepted outputs are now generated fields with their own PRNG stream (so the original seeded trajectories — and every number pinned before the change — survived untouched), the four AI metrics are first-class report sections, and the tiers ship as the versioned contract documented above.

## Scope and honest limits

- **Weekly granularity.** Activation is judged on weekly records, so "within 14 days" means "in week 0 or week 1" — a daily event stream would date activation exactly. The definition, floors, and denominator rules all carry over unchanged.
- **Health rules are documented judgement.** The tier thresholds and the 50% gate are the kind of numbers a customer-success org negotiates quarterly — the claim is that they live in exactly one data table, not that these particular values are right for every product.
- **The anomaly baseline absorbs sustained collapses, and a 4-point MAD is coarse.** A trailing median flags the first collapse weeks hardest, then normalises the new low — stated behaviour of any trailing baseline. And with only 4 points, the MAD can land very small by chance, which makes the detector sensitive: on this deliberately decline-heavy fleet it flags 125 weeks across 72 accounts. Treat the flags as a triage list for a human, not as verdicts; a production deployment would add a persistence rule (flag only if the drop holds) — deliberately not added here, because the brief for this repo was one method, honestly reported.
- **Time to first successful AI task has weekly resolution.** It is the start of the first week with a kept output (week × 7 days), not a timestamp; a daily event stream would refine it without changing the definition. Likewise each prompt is modelled as producing exactly one output in the generator, so total prompts equal total outputs generated — the acceptance *rate* is the informative number, not the raw gap.
- **Archetypes are generation scaffolding, not ground truth.** Health tiers are derived from observed data by the rules, so a generated "steady" account can land at-risk and vice versa; the evals pin the derived counts, not the archetype mix.
- **The API is a demo surface.** It binds 127.0.0.1 only, holds its dataset in memory, and resets on restart.

## Why this project

It takes the adoption-analytics workflow that three real job descriptions asked for in a single sweep — Harvey's customer health, Ramp's activation metrics, Tutor's deployed-AI utilization — and rebuilds it as an analytics-engineering artifact: definitions as code, AI-specific metrics instead of generic usage counts, a data-quality gate, rule-based health a CSM can dispute *and* a versioned contract a renewals forecaster can consume, a tested single-method anomaly detector, and a scorecard that reproduces byte-for-byte. The same discipline a forward-deployed engineer brings to a customer rollout: make "is anyone actually using it — and keeping what it makes?" a number with a definition, a denominator, and an exit code.
